　　该项目属于独立的AI技术研究与工程实践项目，业务背景可以参考政务服务、出入境管理、企业管理、KYC及财务审核等场景，但不代表已经在相关企业或客户系统中部署。所有公开实验优先使用开源数据和合成数据，不依赖企业内部敏感资料。

　　项目希望形成一个可以持续扩展、可开源展示的通用多模态业务Agent框架，而不仅是实现一个固定的自动填表软件。

## 2. 项目背景与核心定位

　　目前已有大量OCR、文档理解、RPA和AI自动填报工具，因此简单的“上传文件、提取信息、自动填写表单”并不是项目的创新重点。

　　本项目重点研究：当系统面对一个未预先配置的业务表单，以及来自多份不同材料的信息时，如何自动理解目标字段、寻找正确的数据来源、识别信息冲突，并可靠生成具有来源证据的填报结果。

　　系统需要尽量减少新表单的人工映射配置工作，同时通过可复用的Skills或历史映射经验降低后续同类任务的处理成本。

　　长期定位是一套通用的多模态业务Agent技术底座，后续可以支持OCR、材料交叉校验、智能问答、智能填报、业务规则、风险预警、报销审核及边缘智能设备协同等能力。

　　但当前阶段不能一次实现所有业务功能，应先从一个可量化评估的核心场景入手，并逐步形成可复用的通用模块。

## 3. 核心研究目标

### 3.1 未知表单理解

　　支持对未预先配置的PDF、Word、Excel等空白表单进行结构分析，识别字段名称、字段类型、必填条件、表格结构以及字段之间的语义关系，生成统一的Form Schema。

### 3.2 多材料语义关联

　　从护照、签证、邀请函、发票及其他材料中提取信息，将不同文件中的实体与目标表单字段关联起来，并正确区分语义相似但业务含义不同的信息。

### 3.3 可信字段映射与校验

　　每个填报字段都应能够关联到明确的信息来源。对于信息缺失、材料冲突或无法可靠判断的情况，系统需要标记异常或请求人工确认，不能为了完成填报而编造结果。

　　证件号码、日期、金额及业务约束等规则优先由确定性程序校验，LLM负责语义理解和必要的辅助判断。

### 3.4 Agent任务编排与经验复用

　　通过Agent工作流组织工具调用、状态管理、异常处理和人工介入。后续保存经过验证的字段映射和业务配置，形成可检索、可审核和可复用的Skills。

　　Skills不是第一版的必要功能，必须先建立没有Skills的基线，才能判断经验复用是否真正改善准确率、适配时间和推理成本。

### 3.5 通用工程架构

　　框架应该具备模型替换、工具扩展和业务适配能力。未来可以提供Python SDK、REST API和MCP接口，并逐步接入Web、Windows桌面软件和边缘设备。

## 4. 已确定的技术选型

| 模块 | 初步方案 |
|---|---|
| 开发语言 | Python |
| 主力模型 | Qwen3.5-9B |
| 模型部署 | vLLM，OpenAI兼容API |
| 计算设备 | 现有4×A100 80GB服务器，首期仅需单卡 |
| OCR | PaddleOCR |
| 结构化数据 | Pydantic、JSON Schema |
| 文档处理 | PDF、Word、Excel解析库 |
| 规则校验 | Python确定性规则 |
| Agent框架 | LangGraph，第二阶段引入 |
| 服务接口 | FastAPI，后续增加MCP |
| 状态与数据存储 | 初期文件存储，后续按需使用PostgreSQL |
| 自动化执行 | Playwright、UIAutomation，后续扩展 |

　　当前决定使用Qwen3.5-9B作为MVP主模型，优先验证基础业务能力，不需要一开始部署复杂的多模型架构。

　　我们也讨论过Qwen3.8-27B、CLEF、CLEF-Flash以及Bonsai 2 27B。其中，27B生成模型可以作为复杂任务和能力上限的对照，CLEF-Flash适合研究快速分类及工具路由，Bonsai 2适合研究极低比特推理和边缘部署。

　　这些模型目前均属于后续实验选项，不作为MVP必需依赖。实际开发前应确认模型权重可获取性、推理框架兼容性及显存要求，不能将尚未验证的部署配置视为已完成。

## 5. 首期MVP范围

### 5.1 选择的业务场景

　　第一个MVP采用“未知出访申请表自动理解与可信填报”作为验证场景。该场景仅用于验证通用架构，未来还需要加入报销审核、企业登记或其他独立业务，以证明框架具备跨场景复用能力。

### 5.2 MVP输入

　　每个任务包含一份此前未预先配置的空白出访申请表，以及模拟护照、签证、邀请函等参考材料。目标表单可以使用PDF或Excel，参考材料可以使用图片、PDF或文本文件。

　　输入不仅包括文件本身，还应有必要的任务描述和明确的模拟业务规则。

### 5.3 MVP输出

　　第一版不必生成最终可提交的PDF或操作GUI，而是输出统一结构的JSON填报草稿，至少包含：

1. 目标表单的字段Schema。
2. 各字段的候选取值和最终建议值。
3. 对应的来源文件、原文证据及可定位信息。
4. 字段的验证状态及异常原因。
5. 需要人工确认或补充的信息。
6. 任务处理状态、错误信息及运行耗时。

　　建议使用Pydantic统一定义FormSchema、Document、ExtractedFact、FieldCandidate、Evidence、ValidationIssue及FillingResult等对象，具体边界可在代码设计时调整。

　　字段状态至少能够区分已验证、存在冲突、资料缺失、需要人工复核和需要计算等情况。

### 5.4 MVP处理流程

　　初期使用固定、可测试的处理链路：

　　输入文件 → 文档解析/OCR → 表单结构理解 → 参考材料信息提取 → 字段语义匹配 → Python规则校验 → 结构化JSON输出。

　　初期可以使用Qwen3.5-9B完成必要的语义理解，但不应将所有数据校验交给模型自由生成。对于无法直接确定的字段，应返回空值和异常信息，而不是猜测填报。

　　首先建立不包含复杂Agent编排的Baseline，随后才能通过相同数据集比较LangGraph、Skills和模型路由带来的实际收益。

### 5.5 首期暂不开发的内容

　　暂不开发完整前端界面、Windows自动操作、复杂多Agent系统、自动审批、生产业务系统对接以及边缘硬件协同。

　　这些模块需要在基础数据处理和可信字段映射通过评测后再逐步增加，避免过早扩大工程复杂度。

## 6. 数据来源与数据集建设

### 6.1 公开数据集

　　项目目前确定可以优先研究以下公开数据资源：

| 数据集 | 用途 | 地址 |
|---|---|---|
| XFUND | 中文及多语言表单结构、字段关系 | https://github.com/doc-analysis/XFUND |
| FUNSD | 扫描表单与键值关系识别 | https://github.com/guillaumejaume/FUNSD |
| CORD | 收据、报销类材料理解 | https://github.com/clovaai/cord |
| DocLayNet | 文档布局和表格区域分析 | https://huggingface.co/datasets/docling-project/DocLayNet |
| DocILE | 发票、订单和商业字段提取 | https://github.com/rossumai/docile |
| MIDV-500 | 身份文件视觉定位与图像处理 | https://github.com/fcakyon/midv500 |

　　第一阶段优先研究XFUND中文数据和CORD数据。上述数据集主要用于单项能力验证，并不直接提供完整的跨材料填报任务。下载和使用前还需检查具体数据许可、访问限制与可再分发条件。

### 6.2 自建合成数据

　　项目需要建立Synthetic Business Data Generator，根据统一的模拟业务事实生成不同格式的材料、空白表单和标准答案。

　　以出访申请为例，先生成虚构人员、证件号码、出访日期、访问单位及邀请信息，再根据这些事实生成模拟护照、签证、邀请函与空白表单。

　　随后有控制地注入数据异常，例如证件日期冲突、缺失字段、名称差异、错误编号、不同语言表达及扫描质量问题，并保留对应的标准答案。

　　生成器应支持固定随机种子、数据版本管理以及开发集和测试集的独立生成。

### 6.3 MVP初始数据规模

　　当前先准备3种不同结构的空白表单，以及15组完整模拟业务任务，其中6组正常案例、5组冲突案例、4组缺失案例。

　　每组任务都需要有Ground Truth，记录正确字段取值、信息来源、字段状态及预期处理动作。

　　这15组主要用于开发调试，不作为最终的未知表单泛化测试。之后需要另行建立未见过的模板族与独立业务实体组成的留出测试集。

　　中期再逐步扩展至约30—50种表单、300—500组业务任务，并增加独立人工校验样本。

## 7. 评价指标与实验设计

　　需要在开发开始时就建立可运行的评价方法，而不是项目完成后才研究如何衡量效果。

　　核心指标包括表单字段识别准确率、字段语义映射准确率、跨材料信息关联正确率、冲突检出率、错误填报率、来源证据正确率、合理拒填率、任务完成率、人工干预次数、处理耗时和推理资源占用。

　　初期至少建立传统规则映射和Qwen3.5-9B直接处理两种可复现基线，后续再与Agent增强方案进行对照。

　　所有正式泛化评测应按照表单模板族和业务实体隔离数据，避免只改变姓名或号码就将相同模板分别放入开发集和测试集。

　　对于错误案例，需要能够定位失败发生在文档解析、语义映射、规则判断还是结果执行环节，从而支持后续有针对性的系统优化。

## 8. 项目后续扩展方向

　　MVP完成后，将核心能力抽象为通用模块，依次增加报销审核、智能问答、企业材料交叉校验和其他业务Agent场景，验证不同业务复用同一套基础能力的可行性。

　　之后再加入LangGraph状态编排、Skills与历史经验复用、MCP工具封装以及不同业务系统的执行适配器。

　　推理优化方面，可以对比Qwen3.5-9B、Qwen3.8-27B和Bonsai 2，并按需要研究CLEF-Flash的工具路由和任务分类能力。比较指标不仅包括模型得分，还包括真实任务成功率、延迟、吞吐量、显存占用及部署维护成本。

　　长期可以进一步研究中心服务器与智能硬件之间的协同，例如将边缘设备负责的证件采集、基础预处理和轻量推理，通过标准接口接入通用业务Agent框架。
